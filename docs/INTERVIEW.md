# 面试问答准备

先自己回答，再看要点。要点只是提纲，面试时要用自己的话、结合自己项目里的数字讲。

---

### 1. prefill 和 decode 有什么区别？为什么 decode 是访存瓶颈？

- prefill：一次处理整个 prompt，大量 token 并行做矩阵乘，算力利用率高，是**算力瓶颈**。
- decode：每步每个序列只生成 1 个 token，但要把全部模型权重和这个序列的 KV cache 从显存读一遍。计算量很小、读的数据量很大，是**访存瓶颈**。
- 所以 decode 阶段要靠加大 batch 摊薄"读一次权重"的成本，而 batch 能开多大取决于 KV cache 能放多少，这就是显存管理重要的原因。

### 2. 一个 token 的 KV cache 占多少显存？以 Qwen2.5-7B 为例。

- 公式：2（K 和 V）× 层数 × KV 头数 × head_dim × 每个数的字节数
- Qwen2.5-7B：2 × 28 × 4 × 128 × 2 字节 = 57,344 字节 ≈ **56 KB / token**
- 一个 4096 token 的序列约 224MB；4090 D 上放完 14.3 GiB 权重，vLLM 日志显示 KV cache 只剩约 6 GiB，能放 111,328 个 token，按 4096 长度算只够 27 路并发。
- 追问：如果没有 GQA（28 个 KV 头），KV cache 会大 7 倍。

### 3. PagedAttention 解决了什么问题？

- 以前的做法给每个请求按最大长度预留一段**连续**显存，带来两种浪费：
  - 内部碎片：预留了 2048，实际只用了 500
  - 外部碎片：空闲总量够，但没有一段连续的空间
- PagedAttention 借鉴操作系统的分页：显存切成固定大小的块，用 block table 记录逻辑块到物理块的映射，按需分配。浪费只剩最后一个块没写满的部分。
- 我的模拟器里：同样 65536 token 的容量，连续预留的平均 batch 是 30.7，分页是 68.7，吞吐上限 2.23 倍；浪费比例从 58% 降到 0.9%。

### 4. 块大小怎么选？

- 太小：块表很长，元数据多；attention kernel 每次只读一小块，访存效率低。
- 太大：最后一个块没写满的浪费变多，前缀缓存的粒度变粗（必须整块相同才能共享）。
- vLLM 默认 16，是个折中。
- 我的模拟数据（实验四）：块大小 1 → 16 → 256，浪费比例 0% → 0.9% → 12.9%，每个序列平均块表长度 858 → 54 → 3.8 项，吞吐上限 2.25× → 2.23× → 1.99×。16 以下吞吐几乎不再涨，块表却线性变长。

### 5. continuous batching 和 static batching 的区别？

- static：一批请求一起进、一起出，短请求要等长请求生成完，GPU 空转。
- continuous（iteration-level scheduling）：每个 decode 步都可以让新请求加入、让完成的请求离开，batch 始终是满的。
- 分页显存管理是 continuous batching 的基础：请求随时进出，必须能随时分配和回收零散的显存。

### 6. 显存不够了怎么办？抢占的两种方式？

- recompute：直接释放被抢占请求的 KV cache，之后重新 prefill（prompt + 已生成部分）。实现简单，短序列划算。
- swap：把 KV cache 换到 CPU 内存，之后再换回来。省计算，但占 PCIe 带宽。
- 我的模拟器用的是 recompute，抢占"最后进来的"请求（LIFO），避免已经跑了很久的请求被反复踢出。
- 怎么少抢占：准入时留水位线（见第 18 题）。

### 7. 前缀缓存是怎么实现的？

- 每个写满的块算一个哈希：hash(前一块的哈希, 本块的 token)，形成哈希链。
- 新请求进来时，从第一个块开始依次查表，连续命中的块直接复用（引用计数 +1），从第一个没命中的块开始正常分配。
- 为什么要哈希链：attention 的 K/V 依赖前面所有 token。两个块内容相同但前文不同，KV 值也不同，不能共享。
- 为什么只缓存写满的块：没写满的块后面还会被写入，内容会变。
- 哈希碰撞：64 位哈希碰撞概率极低但不是零，碰撞了会输出错误结果。vLLM 后来提供了 SHA-256 选项。
- 请求结束后缓存还在吗：看实现。我先做的版本引用计数一归零就失效，后来加了 LRU 延迟驱逐（见第 17 题）。

### 8. 写时复制用在什么场景？

- 一个 prompt 生成多个回答（OpenAI 接口的 `n > 1`）、beam search：多个序列共享同一个 prompt 的 KV。
- `fork` 只加引用计数不拷贝；某个序列要往一个被共享的块里写时，才分配新块并把内容拷过去。
- 满块不会触发复制，因为新 token 总是写进新块；只有最后一个没写满的共享块才需要复制。

### 9. TTFT、TPOT、ITL 分别是什么？为什么要看 P95/P99？

- TTFT：从发请求到收到第一个 token，用户感受到的"反应速度"，主要受排队和 prefill 影响。
- TPOT：生成阶段平均每个 token 的耗时，决定"打字速度"。
- ITL：相邻两个 token 之间的实际间隔，能看出抖动（比如被别的请求的 prefill 卡住）。
- 平均值会被大量正常请求"稀释"，看不出尾部用户的糟糕体验；线上 SLO 一般按 P95/P99 定。

### 10. 并发越高，吞吐和延迟怎么变？怎么选部署的并发数？

- 并发升高 → batch 变大 → 吞吐上升，但每个 token 要等更大的 batch 算完，TPOT 变大。
- 到 KV cache 放满或算力打满后，吞吐不再增长，延迟继续变差，甚至触发抢占。
- 选法：先定 SLO（比如 P95 TPOT < 50ms、P95 TTFT < 1s），在吞吐-延迟曲线上找满足 SLO 的最大吞吐点。

### 11. AWQ 和 GPTQ 有什么区别？INT4 量化为什么能加速？

- GPTQ：逐层量化，用二阶信息（近似 Hessian）把量化误差补偿到还没量化的权重上。
- AWQ：观察到少数通道对应的激活值很大、这些权重更重要，通过按通道缩放来保护它们，不需要反向传播。
- 加速原因：decode 是访存瓶颈，INT4 权重只有 BF16 的约 1/4，读得更快；省下的显存还能给 KV cache，开更大的 batch。
- 高并发时转为算力瓶颈，反量化有额外开销，优势会缩小。
- 实测（RTX 4090 D）：单并发 TPOT BF16 15.4 ms、GPTQ-INT8 9.0 ms、AWQ-INT4 5.7 ms，和"权重字节数 ÷ 1008 GB/s"的理论下限 14.0 / 7.7 / 4.4 ms 对得上；并发 128 时 AWQ 吞吐只比 BF16 高 10%，GPTQ-INT8 反而低 2%。

### 12. FP8 KV cache 有什么用？

- KV cache 每个数从 2 字节变成 1 字节，同样显存能放约 2 倍 token，最大并发和长上下文能力都提升。
- 代价是精度损失，一般影响很小，但需要评估。
- 实测：同条件下 KV 容量 111,328 → 209,648 token（1.88 倍，FP8 配置的 CUDA graph 预留多 0.35 GiB）；单并发速度不变，并发 128 时 TPOT 48.9 → 44.0 ms，因为大 batch 下 KV 读取量也减半了。

### 13. 你的压测工具怎么保证结果可信？

- 预热：避开 CUDA graph 捕获、显存分配等一次性开销。
- `ignore_eos`：强制每个请求生成固定长度，否则模型提前结束会让不同配置不可比。
- 固定输入、输出长度和随机种子，每轮请求数是并发数的 4 倍以上，保证分位数有足够样本。
- token 数以服务端返回的 `usage` 为准，不靠自己估算。
- 用 Little 定律交叉验证：并发数 ≈ 吞吐 × 平均延迟。

### 14. 为什么压测客户端用线程而不是 asyncio？有没有问题？

- 发请求、等响应是 IO 操作，等待时会释放 GIL，几百个线程完全够用，代码也更直观。
- 并发上千时线程切换开销变大，客户端本身可能成为瓶颈，这时应该改成 asyncio + aiohttp（vLLM 官方压测脚本就是这样）。
- 判断客户端是不是瓶颈：看客户端机器的 CPU 占用，或者把客户端放到另一台机器上对比结果。

### 15. 你的模拟器有什么局限？

- 只建模显存，不建模计算，每步时间都当成一样长。真实情况下 batch 越大单步越慢。
- 被抢占请求的重算 token 数统计了（实验一里分页方案要重算 48 万 token），但没有折算成时间，分页方案的倍数偏乐观。
- 抢占只有 recompute，没有 swap；请求是一开始全部排队的闭环负载，没有模拟到达过程。
- 能说出局限，比假装没有局限加分。

### 16. 线上 TTFT P99 突然变高，怎么排查？

- 先看是排队还是计算：请求在调度队列里等了多久？
- KV cache 满了吗？有没有频繁抢占？
- 是不是来了一批超长 prompt，prefill 卡住了其他请求？（可以考虑 chunked prefill：把长 prompt 切块，和 decode 混在一起跑）
- 前缀缓存命中率是不是掉了？（比如 system prompt 被改了）

### 17. LRU 延迟驱逐是怎么实现的？为什么需要它？

- 问题：引用计数一归零就把块从前缀缓存里删掉，那么一个冷门应用的请求结束后，下一个同样前缀的请求又要重新 prefill。
- 做法：归零的满块不回空闲栈，而是放进 LRU 队尾，内容和哈希登记都保留，新请求照样能命中（命中后从 LRU 里拿出来，引用计数 0 → 1）。分配新块时先用真正空闲的块，没有了才驱逐 LRU 队头，同时删掉它的哈希登记。
- 细节：命中 LRU 里的块时，它就不能再算作"可用空间"，否则准入检查会多算（我专门写了 `lru_hits_are_not_counted_as_free_space` 测试）；序列逆序释放，尾部块先进 LRU、先被驱逐，前缀块留得更久。
- 数据（实验五，64 个应用 Zipf 分布）：前缀命中率 48.4% → 60.5%，需要 prefill 的 token 再少 23%。

### 18. 准入水位线是什么？取多少合适？

- 准入新请求时，要求分配完之后至少还剩总块数的 x% 空闲，给正在 decode 的序列留余量。否则新请求刚放进来，下一步老请求长出新块时就没地方了，只能抢占。
- 只在准入时检查，decode 追加 token 可以用掉水位线以下的块；系统空的时候不检查，否则大请求可能永远进不来。
- 数据（实验三）：1% 水位线抢占 469 → 48 次，重算 token 减少 91%，吞吐只降 0.6%；到 10% 吞吐降 9%。所以取 1% 左右（vLLM V0 的 BlockSpaceManager 默认 watermark 也是 0.01）。

### 19. 闭环压测和开环压测有什么区别？

- 闭环（固定并发）：同时最多 N 个请求在飞，一个结束才发下一个。服务变慢时发送速率也跟着降，所以永远测不出"排队爆炸"，适合画吞吐-延迟曲线。
- 开环（泊松到达）：请求按设定速率到达，不管前面的有没有结束，更接近线上真实流量。到达率超过服务能力时，排队时间会持续增长，TTFT 尾延迟暴涨。
- 我的 bench.py 两种都支持：默认闭环，`--request-rate` 打开泊松到达（请求间隔服从指数分布）。
